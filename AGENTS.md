# JSLAB agent guidance

JSLAB is a scientific JavaScript desktop environment built with Electron. User scripts use the `.jsl` extension and run in a persistent workspace. Use the JSLAB MCP tools to execute JSLAB code; a plain Node.js process does not provide the JSLAB runtime or its scientific functions.

## Use a shared JSLAB session

- Read [the MCP server section](docs/documentation.md#mcp-server) for setup, tool arguments and execution limits. The same guidance is available through `jslab://mcp-guide`.
- Start with `list_sessions` and `get_session_status`. Verify that the intended desktop session is ready. Configure an explicit session when several are shared.
- Consult `get_help` for unfamiliar functions instead of guessing APIs. Use a function name, `lib.function`, or `type: "category"` with a category name.
- Use `evaluate_code` for small calculations and `run_file` for saved `.jsl` scripts. Pass absolute file paths and an explicit `cwd` when relative data paths matter.
- The workspace and working directory persist between calls and are shared with the user. Inspect existing variables before replacing them. Avoid clearing the workspace or closing figures unless the task requires it.
- Inspect `result.success`, captured output and error details. `check_code` diagnostics must also be checked for error severity. Execution success alone does not validate a numerical result.
- When a tool returns `status: "running"`, poll `get_execution` using the returned execution ID. Do not submit the same calculation again just because the tool stopped waiting or the connection failed.
- Use `interrupt_execution` to request a stop, then confirm completion. Interruption terminates JavaScript through the main-process debugger and runs registered resource cleanup without clearing the workspace. Native blocking operations may still require a sandbox reset, which discards the workspace.
- Loop checkpoints are not required. Use `pause_execution`, `get_debug_state`, `inspect_debug_object` and `evaluate_debug_expression` to inspect paused frames, then `resume_execution` to continue or step. Frame handles expire on resume.
- Use `list_workspace` and `read_variable` for focused inspection. Previews are bounded and are not lossless data exports.
- Use `list_figures` and `export_figure` to inspect plots. Export to a task-specific absolute path. Raster exports up to 4 MiB can return an image directly to the agent.
- For repeatable checks, create a `.jsl` test script whose assertions throw on failure, then call `run_test_file`. Background callbacks must be awaited if their results determine success.
- Code runs with the user's JSLAB permissions. Keep file writes, external processes and device operations within the user's requested task. Do not print, commit or share session descriptor credentials.

## Work on the repository

- Translate user-visible UI text through `config/lang.json` for `en`, `rs` and `rsc`. Run `npm run check-ui-translations`. Mark intentionally fixed HTML text locally with `lang-fixed`, or an adjacent JavaScript literal with `/* lang-fixed */`; do not use these annotations to exempt text that should be translated.
- Keep application translation IDs contiguous and numerically ordered from `1`; update all references together when renumbering. Compiler translations belong in `lib/openmodelica-jslab/config/lang.json` and use ordered, contiguous `omjsl-1`, `omjsl-2`, etc. Update their code and metadata references together. Other compiler catalogs belong in `metadata/`, handwritten library code in `js/`, and generated native scene bindings and WASM in `animation/`. Keep installed catalogs readable, use `.js` source files, and compress catalogs only for browser distribution builds. Apply layout and code changes to the compiler fork sources as well as the installed library.

- Follow nearby source conventions: application classes use `PRDC_JSLAB_*`; OpenModelicaJSLAB-owned library classes use `PRDC_OMJSL_*`. Use two-space indentation, `if(...)` formatting, descriptive JSDoc comments, and the existing file header format.
- Keep class names descriptive of their file's feature or service. Backend filenames identify the service directly, such as `renderer.js`; use `*_ADAPTER` for injected host adapters and avoid `-platform` filenames or `*_PLATFORM` class names. Preserve registered workspace API names and external library interfaces.
- Electron starts directly from `js/backend-electron/main-process.js`; its `start()` method initializes main-process arguments and configuration. Keep development suite coordination in `js/dev/run-app-tests.js` and load Simulate project services on demand. Do not restore a root `js/init.js` wrapper or use renderer startup helpers in the main process.
- Electron main-process services and adapters are in `js/backend-electron`, and browser adapters are in `js/backend-web`. Keep main-window controllers in `js/main`, the Editor in `js/editor`, Simulate in `js/simulate`, and smaller auxiliary window controllers in `js/windows`. Inject platform services instead of importing a backend. Simulate's entry controller is `simulate.js`; its document, library, properties, diagram, interaction and compilation controllers belong alongside it. Sandbox modules remain in `js/sandbox`, and the stdio adapter remains in `js/mcp`.
- JavaScript linting and CodeMirror diagnostic conversion use `js/code/lint.js` in both hosts. Keep application rules in `config/config.js`; do not create backend-specific lint implementations.
- Keep Editor breakpoints, debugger controls and debugger panes in `js/editor`. Reserve `js/code` for reusable CodeMirror editing, linting, search and documentation support.
- Keep cross-feature utilities in `js/other-shared`. Code used by both backends stays with its feature; using both Electron and the browser does not make it a cross-feature utility.
- Route application settings through the injected storage service (`get`, `set`, `has`, `delete`, `clear`) and secrets through its secret methods. Keep direct `localStorage` access and `electron-store` imports inside backend storage implementations; runtime capability probes may report browser storage availability. Preserve existing settings when migrating older storage keys.
- Both backend storage services extend `js/other-shared/storage.js` for common setting operations and migration. Keep persistence primitives and secret policy in the backend. Use the actual `PRDC_PANEL` class in common controllers and pass `platform.panel_store` explicitly; do not wrap it in backend subclasses solely to inject storage.
- Use `js/other-shared/language.js` for renderer translations in both hosts. Inject storage and document-rendering options at startup; do not duplicate translation lookup, formatting or DOM updates in backend modules. Browser managed iframe initialization belongs in `js/backend-web/init-frame.js`.
- Keep Simulate project open/import/save policy in `js/simulate/project.js`, with injected host file reads, writes and dialogs. Keep debugger request response formatting in the common dispatcher. Native window language setup uses the renderer adapter; browser windows use the common language preference adapter.
- Reuse the feature-owned bases for Command Window modules, boundary-following bookkeeping, spreadsheet formatting and buffered networking endpoints. Presentation content helpers and render lifecycle live in `js/windows/presentation-content.js`; emit that source with exported viewer scripts so standalone presentations remain self-contained. Browser capability and parent-bridge detection use `js/backend-web/browser.js` in both host and sandbox contexts. Share source-audit utilities in `js/dev/source-analysis.js` and test fixtures through the existing tester and GUI support modules.
- Keep native application integrations (OpenModelica, FreeCAD and spreadsheet COM links) and their process transports in `js/backend-electron`. Preserve their workspace APIs through environment factories. Documentation descriptors must point to the owning source files and include inherited API methods when shared base classes are used.
- Name backend files by their actual responsibility. Electron's process root is `main-process.js`; the browser application host is `app-host.js`. Use matching filenames only for equivalent services, such as `files.js`, `sandbox-host.js`, `window-manager.js`, `storage.js` and `simulate-assets.js`. Backend modules contain host services and transport adapters; feature behavior stays in its feature folder. Assistant UI, conversation state, provider requests, tool routing and context coordination live in `js/windows/assistant.js`. Assistant uses the application storage service's secret methods; Electron storage encrypts persisted secrets and browser storage keeps secrets in memory. Do not add Assistant-specific credential adapters. Presentation Editor controllers, including the inline editor, belong in `js/presentation-editor`. LaTeX editor controllers belong in `js/latex-editor`. Their bootstraps and host services stay in the backend. Browser worker and iframe runtime entry points belong in `js/sandbox`.
- Host debugger adapters extend `js/other-shared/debugger-state.js` for common state, settings and validation. Sandbox hosts compose `js/other-shared/debugger-dispatcher.js` for debugger command routing, and window adapters extend `js/windows/window-manager.js` for feature definitions and focus policy. Keep Chromium protocol, shared-memory messaging, native-window operations and process ownership in their respective host adapters. Do not introduce a base class for unrelated host responsibilities.
- Keep native IPC authorization and browser messaging in their adapters. Browser asset resolution and lazy script loading belong to `js/backend-web/files.js`. The browser Simulate window bridge is `simulate-host.js`, separate from compiler asset loading in `simulate-assets.js`.
- Both backends instantiate `js/main/main.js`. Keep main-window behavior in `js/main`; `js/backend-web/app-host.js` owns browser host services and forwards its bridge to these controllers. The GUI component suite checks common controller handlers; the browser suite checks browser adapter handlers and real browser integration.
- Keep `js/sandbox` independent of the host except for `jslab-env-electron.js` and `jslab-env-web.js`. Runtime entry points, browser worker transport, debugger instrumentation and remote UI machinery belong in their backend folders. The environment owns module loading, worker construction and presentation transport selection. Public API modules retain feature names and are registered in `config.SUBMODULES`; related implementations retain their parent prefix. Both hosts use `presentation.js`; backend presentation transports handle native HTTP/bundling or browser blob/iframe delivery. Documentation-only declarations use `*-doc` and belong in `DOC_SUBMODULES_ADDITIONAL`.
- A filename or a CommonJS export does not expose workspace commands. Register public API modules explicitly; load private helpers through their owning module before runtime `require` overrides. Prefix implementation fields and methods with `_` so they are not exported as workspace variables or commands. Keep a single shared public module implementation and select host adapters through the environment. Update `backend-web/sandbox-modules.js` when changing the registered constructor set.
- Keep internal sandbox module access under `jsl.inter`. Reuse the existing evaluator and environment methods for agent execution.
- Numerical and AlphaShape operations use shared WASM modules in desktop, browser and workers. Initialize `jslab-wasm-loader` before constructing the runtime. Implement algorithms in the C++ cores and bindings in `cpp/*-wasm.cpp`; keep host I/O and subprocess operations in the environment. Rebuild with `npm run build-native-wasm` before testing C++ changes. Do not introduce separate JavaScript numerical fallbacks or application Node-API bindings.
- Keep stdout free of application messages in the stdio adapter. Send diagnostics to stderr.
- The terminal frontend is in js/cli and owns a hidden Electron runtime through the existing local automation bridge. Keep CLI sessions isolated from desktop instance routing. Run node js/dev/run-cli-tests.js for real batch and Windows terminal integration checks.
- Windows packaging uses js/dev/prepare-cli.js before signing to prepare the console host and its runtime manifest. Keep the console frontend separate from the GUI runtime, and verify the packaged application with node js/dev/run-cli-tests.js --packaged=dist/win-unpacked.
- Keep Windows installer configuration in config/installer.nsh. Generate the Windows launcher with js/dev/prepare-cli.js; do not add a tracked batch launcher or PowerShell PATH helper. Keep CLI and GUI tests with their modules, and do not add a dev test suite or place build-only documentation tests in other-shared.
- Keep browser adapters in js/backend-web, the browser HTML shell in html/web.html and its styles in css/web.css. Reuse the existing HTML and CSS folders instead of adding a top-level web asset folder.
- Tests use `PRDC_JSLAB_TESTS` and export `MODULE_TESTS`. Run a relevant suite with `node js/dev/run-test-suite.js --folder=backend-electron` or `--folder=sandbox`; `--test-module=automation` selects matching test modules.
- Put each module's `.test.js` files directly in its `tests` folder; create that folder when needed. Avoid extra GUI/platform subfolders under `tests`. Keep GUI test support and launchers directly in `js/dev`; retain the application's existing `js/other-shared/tester.js`. Do not add a standalone GUI testing documentation file.
- Documentation is generated by `js/dev/make-doc.js` from the templates in `dev`. Edit the MCP section in `dev/documentation_template.md`; the generator shares it with HTML, TeX and PDF. Run `npm run make-doc` to update the generated documentation, including `docs/documentation.md`.
- Preserve unrelated user changes and keep generated artifacts out of a change unless the change requires them.
